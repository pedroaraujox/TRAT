## Project Overview

**TRAT** is a Windows-based backup orchestration system with a centralized management panel. It monitors multiple client machines, orchestrates backups to AWS S3, deduplicates files via SHA256, and provides real-time status monitoring.

**Architecture**: Agent (Windows Service + Tray App + Installer GUI) ↔ API (ASP.NET Core) ↔ PostgreSQL/SQLite

| Layer | Technology | Details |

## Critical Build & Publish Workflow

### Development (Local/Windows)

1. **Modify code** in `src/Agent/*` or `src/ControlPlane/*`
2. **Rebuild affected project**: `dotnet build src/Agent/... -c Release` or `dotnet build src/ControlPlane/... -c Release`
3. **Publish artifacts** (must be done, not just compile):
   - Agent changes → `scripts\agent\Publish-Agent.ps1`
   - ControlPlane changes → `scripts\controlplane\Publish-ControlPlane.ps1`
   - Both → run both scripts
4. **Validate on packaged artifacts**, not bin/obj files or IDE execution
5. **Start local dev server**: `.\Iniciar-TRAT.ps1` (uses `artifacts\trat-local\TRAT.ControlPlane.Local`)

### Standard Release Flow

```powershell
.\Liberar-TRAT.ps1
```

This single command:
- Publishes Agent (to `artifacts\agent-package`)
- Publishes ControlPlane (embeds Agent artifacts into `artifacts\trat-local`)
- Runs smoke tests (dry-run Agent, login, basic UI checks)
- Generates release report to `artifacts\release-reports`

**Optional flags**:
```powershell
.\Liberar-TRAT.ps1 -SkipAgentPublish                    # Skip Agent, update ControlPlane only
.\Liberar-TRAT.ps1 -SkipSmokeTest -AllowIncompleteRelease  # Publish without validation
.\Liberar-TRAT.ps1 -ResetLocalState                     # Clear test DB/settings before validation
```

## Database & Configuration

### SQLite (Development)

- Location: `data/controlplane.db` (relative to ControlPlane package root)
- Auto-created on first startup via `EnsureCreatedAsync()`
- Preserved across rebuilds by `Publish-ControlPlane.ps1` backup/restore cycle
- Configured in `appsettings.json` → `ControlPlane:Database:SqlitePath`

### PostgreSQL (Production)

- Connection string via `ConnectionStrings:DefaultConnection` (env var in docker-compose)
- Activated via `ControlPlane:Database:UsePostgres=true`
- Program.cs detects which DB to use at startup

### Configuration Sources (in order of precedence)

1. Environment variables (`ASPNETCORE_*`, `ConnectionStrings__*`, `ControlPlane__*`)
2. `appsettings.Production.json` (prod deployment)
3. `appsettings.Local.json` (dev overrides, git-ignored)
4. `appsettings.json` (defaults)

### Key Settings

```json
{
  "ControlPlane": {
    "Security": {
      "AgentToken": "token used by Agent to call /api/v1/agents/* endpoints",
      "AdminToken": "token for internal admin APIs (if needed)"
    },
    "BootstrapAdmin": {
      "Email": "initial admin account created on first startup",
      "Password": "set via env in docker-compose"
    },
    "Database": {
      "UsePostgres": true,           // Set to true for prod
      "SqlitePath": "data/controlplane.db"  // Used if not PostgreSQL
    }
  }
}
```

## Agent vs. ControlPlane: Key Separation

### Agent Responsibilities
- Runs on Windows hosts as a service + user-facing tray app
- Scans local filesystem per configured policy
- Uploads to S3 with SHA256 deduplication (skips re-upload if hash matches)
- Reports job status back to ControlPlane API
- Never deletes from S3 (immutable backup principle)

### ControlPlane Responsibilities
- Web UI for operator (login, manage customers/hosts, see job status)
- REST API for Agent telemetry & onboarding
- Stores host configuration, backup policies, job history
- Serves Agent downloads (Setup.exe, ZIP)
- Does NOT execute backups itself (Agent pulls policy, executes locally)

### Communication Flow
1. Agent calls `POST /api/v1/agents/enroll` (with token) → ControlPlane registers host
2. Agent polls `GET /api/v1/agents/{hostId}/policy` → ControlPlane returns backup policy
3. Agent executes backup locally, then POSTs results to `POST /api/v1/agents/{hostId}/jobs`
4. ControlPlane stores results, UI shows them

## Important Rules (from project.rules.json & CHECKLIST)

### Mandatory Practices

1. **Always rebuild/republish before validating**
   - Compiling source code is not validation
   - Test against packaged artifacts (ZIP, Setup.exe, local package)

2. **Preserve test state across iterations**
   - When changing Agent/ControlPlane, update in-place if possible (don't reinstall from scratch)
   - Only reinstall if the change is to the installation flow itself
   - `Publish-ControlPlane.ps1` auto-backs up `data/`, `logs/`, and `appsettings.Local.json`

3. **Validate ponta-a-ponta** (end-to-end)
   - UI changes → open real page, verify visual/behavior
   - Download links → actually download file from page
   - Agent install → run installer, verify service starts
   - Backup execution → run manually, check S3 and painel status
   - Don't skip this for "simple" changes

4. **No S3 deletes allowed**
   - Agent can only PutObject, ListBucket, HeadObject, GetBucketLocation
   - Bucket must have Object Lock enabled, versioning on, public access blocked
   - This prevents accidental ransomware via backup compromise

5. **Windows compatibility**
   - PowerShell scripts must work with PowerShell 5.1 (no 6+/Core features)
   - Agent must run as Windows Service (not console app)
   - ControlPlane must run as Windows Service (via `UseWindowsService()`)
   - No dependency on dev-only features (localhost paths, hardcoded IPs, etc.)

### Exit Gates

Don't consider a task done if:
- Release report shows `INCOMPLETE` or `FAILED`
- Validation was only on source code, not the real packaged artifact
- Smoke test (dry-run, login, heartbeat) failed
- Data state was reset when preserving it was possible

## Agent Setup.exe Special Behavior

The `TRAT.Agent.Setup.exe` is a standalone executable that:
1. Checks if package files exist in same directory or parent folders
2. If not found, extracts embedded payload (ZIP) to `%LOCALAPPDATA%\TRAT\AgentSetupPayload`
3. Proceeds with installation from extracted payload
4. No need for separate ZIP download; one .exe file is sufficient

The payload is embedded during the publish phase by `scripts/agent/Publish-Agent.ps1` via conditional `<EmbeddedResource>` in `.csproj`.

## Known Limitations & Workarounds

- **PowerShell 5.1 only**: Scripts don't use PSv6+ features; tested on Windows Server 2012+
- **SQLite concurrency**: Dev-only; production must use PostgreSQL (docker-compose enforces this)
- **Data protection**: Keys stored in `data/keys` via DPAPI on Windows; on Linux/Docker, consider external key store if needed
- **No migrations framework**: Uses `EnsureCreatedAsync()` for schema; changes to models require manual migration or rebuild
- **Heartbeat interval**: 60s by default; configure in policy if client needs faster/slower checks

**API not responding?**
```powershell

Get-Service -Name "TRAT ControlPlane" | Select-Object Status

# Check app logs
Get-Content artifacts\trat-local\TRAT.ControlPlane.Local\logs\*.log -Tail 50

# Test health endpoint
Invoke-WebRequest http://localhost:5000/api/v1/health -UseBasicParsing
```

**Agent not uploading?**
```powershell
# Check if service exists and is running
Get-Service -Name "TRAT Agent" | Select-Object Status

# Check agent log on the host

# Run installer again, fill token/bucket/region, click "Testar ControlPlane"
```

